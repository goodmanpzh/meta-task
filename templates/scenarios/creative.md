For the `instruction.md` you generate, **do NOT follow any predefined writing template**. Instead, creatively simulate how a real user might actually communicate their request.

Real users don't write in consistent styles. Their messages are shaped by their habits, tools, mood, context, and communication medium. Your job is to brainstorm and produce a realistic, natural user input that feels genuinely human — something that could actually land in a chat window, terminal, email, or ticket system.

**Key principles**:
- **Authentic diversity** - Each generated instruction should feel like it came from a different real person using a different communication medium
- **Natural imperfections** - Real messages have typos, abbreviations, mixed languages, incomplete thoughts, changed minds mid-sentence, or afterthoughts tacked on
- **Varied formats** - The input could take any realistic form a user might produce
- **No forced pattern** - Don't default to any particular structure. Let each one be genuinely different from the last

**Brainstorm directions for user input styles** (use as inspiration — invent your own):
- Voice-to-text transcription with recognition errors and run-on sentences, no punctuation
- Mixed language (e.g., English with Chinese/Japanese/Spanish terms, code-switching mid-sentence)
- A message that was clearly edited multiple times — strikethroughs, "actually never mind the above", corrections
- Bullet points dumped from a meeting notes app, half-complete, with action items mixed in
- A forwarded Slack thread or email chain where the actual request is buried
- Screenshot-description style: "see the attached screenshot" (no screenshot) then trying to describe what they saw
- Telegram/WeChat style: multiple short messages instead of one long one, sent in rapid succession
- A request phrased entirely as a series of questions: "Is it possible to...? What if I...? Could you...?"
- Someone clearly copy-pasting from ChatGPT/documentation and adding their own notes in brackets
- An overly formal enterprise-speak request: "Please action the implementation of the aforementioned feature"
- Emoji-heavy casual style: "hey 🙏 can u help me build this thing 🔧 need it by tomorrow 😭"
- A diff or patch pasted with "apply this but change X"
- Pseudo-code or whiteboard-sketch style: rough logic flow instead of precise requirements
- Stream of consciousness while thinking through a design: "ok so I think we need X... and then Y feeds into Z... wait actually maybe..."
- A ticket auto-generated by a monitoring system (PagerDuty, Grafana alert) with the user adding a one-line comment

**Remember**: The goal is to simulate the full spectrum of how real humans actually type requests in practice. Each generated instruction should feel like it was written by a real person in a real moment — messy, human, and authentic. Be creative about the *communication style*, not the task type — the task itself should be about building, creating, analyzing, configuring, or implementing something.
